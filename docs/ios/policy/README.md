# Tailscale iOS AppConfig policy template

This directory is the iOS/[AppConfig](https://www.appconfig.org/ios.html) analog of `docs/windows/policy/`: instead of an ADMX/ADML pair for Windows Group Policy, it's an XML spec for Apple's Managed App Configuration mechanism, which MDM solutions (Jamf, Intune, Kandji, SimpleMDM, etc.) use to push key-value configuration into managed apps.

`tailscale.appconfig.xml` declares the Tailscale system-policy keys registered in `util/syspolicy` that support iOS, in the spec format consumed by [`jamf/AppConfig-Generator`](https://github.com/jamf/AppConfig-Generator) (the tool behind the [AppConfig Generator](https://generator.appconfig.jamfresearch.com/generator)). It is not code, and it does not by itself change how the Tailscale iOS app behaves: the app's config-reading code lives in Tailscale's closed-source iOS app repo, outside this project. This file only helps an MDM admin author and test a valid AppConfig payload for the app, bundle ID `io.tailscale.ipn.ios`.

## This file is generated

As of this writing, `tailscale.appconfig.xml` is generated by `cmd/genpolicydocs` from the policy definitions in `util/syspolicy` (`policy_keys.go`'s registry for types/platforms, `util/syspolicy/policydoc` for labels/descriptions), not hand-maintained. Regenerate it with:

```bash
go run tailscale.com/cmd/genpolicydocs
```

Do not hand-edit this file directly: edits will be overwritten the next time someone regenerates it. To change a key's label or description, edit `util/syspolicy/policydoc/policydoc.go`. To change which platforms a key applies to, edit its `setting.NewDefinition(...)` call in `util/syspolicy/policy_keys.go`.

**Known gap:** `HiddenNetworkDevices`, `ManageTailnetLock`, and `VPNOnDemandSettings` were present in the original hand-written version of this file but are not yet registered anywhere in `util/syspolicy/pkey/pkey.go` or `policy_keys.go`, so the generator cannot include them. They need a `pkey.Key` constant and a `setting.NewDefinition(...)` entry before they can reappear here.

Fields are grouped into named `fieldGroup`s by `util/syspolicy/policydoc`'s `Category` field, one of five (`Configure the auto-update settings`, `Configure the exit node settings`, `Show contact information for your organization`, `Other settings`, `Change the visibility of UI items`), the verbatim section headings at https://tailscale.com/docs/features/tailscale-system-policies, the same categories `docs/windows/policy/`'s ADMX category tree uses. To change a key's category, edit its `Category` in `policydoc.go`.

## Generating a deployable plist and testing with Jamf

1. Open the [AppConfig Generator](https://generator.appconfig.jamfresearch.com/generator) (or run `jamf/AppConfig-Generator` locally). Use this one, not the `beta.appconfig.jamfresearch.com` version; see the known-incompatibility note below.
2. Load `tailscale.appconfig.xml` as the spec file.
3. Fill in the values you want to test with (e.g. a test `LoginURL` or `Tailnet`) and generate the plist.
4. In Jamf Pro, open the Tailscale app's App Configuration screen (bundle ID `io.tailscale.ipn.ios`) and paste or upload the generated plist. Jamf Pro expects the content inside the `<dict>` tags of the generated XML; Jamf School expects the content inside the `<plist>` tags, so see the generator's own output for both variants.
5. Scope the configuration to a test device or group, push it, and confirm the keys appear in the Tailscale app's managed configuration on-device.

## "Not configured" defaults

The AppConfig Generator (and Apple's AppConfig mechanism generally) always writes every declared key into the resulting plist, with no way to omit an unconfigured key from the output. So instead of trying to represent "not configured" by omission, every enum-typed key (every `PreferenceOptionValue` key, whose real values are `always`/`never`/`user-decides`, and every `VisibilityValue` key, whose real values are `show`/`hide`) gets a `"Not configured"` option that submits an empty string. That's not a workaround: `util/syspolicy/ptype` parses an empty string identically to the key being entirely absent for both value types (`UnmarshalText` explicitly falls back to the unmanaged default for any unrecognized input, including `""`), so leaving a field on "Not configured" in the generator does not force any policy.

This spec is written to be compliant with, and has been tested against, the generator at https://generator.appconfig.jamfresearch.com/generator. Use that one, not the `beta.appconfig.jamfresearch.com` version, which has known compatibility issues with the blank values this spec relies on for "Not configured" options.

## Array fields come out non-empty by default

`AllowedSuggestedExitNodes` (currently the only `StringListValue` key that's both registered in Go source and iOS-supported) has no default value, so an unconfigured admin console leaves it with one blank text entry, and the generated plist has `<array><string/></array>` rather than a truly empty `<array/>`. This looks odd but is harmless (an empty-string device ID never matches a real one). Leave array-typed keys without a `defaultValue` (as `AllowedSuggestedExitNodes` is now); giving them one caused problems when tested against the generator above.

## Keeping this file accurate

Since this file is generated (see above), keeping it accurate means keeping its two Go-side inputs accurate: platform applicability lives in each key's `setting.NewDefinition(...)` call in `util/syspolicy/policy_keys.go`, and labels, descriptions, and categories live in `util/syspolicy/policydoc/policydoc.go`. Treat https://tailscale.com/kb/1315/mdm-keys and https://tailscale.com/docs/features/tailscale-system-policies as the sources of truth when writing or updating `policydoc` entries.

## Scope

This is a first pass meant for hands-on testing, not a final or exhaustive artifact:

- Platform filtering relies on the `platforms` metadata in `policy_keys.go`. Most `VisibilityValue`-typed keys (UI show/hide toggles) have been checked against unambiguous evidence and a handful of other keys have too, but not every key in either category has actually been audited yet (e.g. `SuggestedExitNodeVisibility` is left at the universal default because nothing about it has been examined, not because it was verified universal). Unaudited keys default to "supported everywhere," so they're over-included here rather than under-included, an accepted tradeoff for now. See `docs/tvos/policy/README.md` for why the platform data is more conservative for those keys than it could be.
- Constraints are limited to enum value lists (e.g. `always`/`never`/`user-decides`, `show`/`hide`); there's no regex or min/max validation on freeform strings like `LoginURL` yet.
- `docs/windows/policy/tailscale.admx` and `en-US/tailscale.adml` are generated by this same `cmd/genpolicydocs` from this same `util/syspolicy` source; see `docs/windows/policy/README.md` for how that output differs from the hand-written file it replaces.
