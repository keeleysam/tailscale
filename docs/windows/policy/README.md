# Tailscale Windows Group Policy (ADMX/ADML) templates

`tailscale.admx` and `en-US/tailscale.adml` are the Windows Group Policy Administrative Template pair for the Tailscale Windows client: `tailscale.admx` declares each policy (registry path, value type, UI control shape), and `tailscale.adml` supplies the localized display names, help text, and admin-console presentation details it references.

## These files are generated

As of this writing, both files are generated by `cmd/genpolicydocs` from the policy definitions in `util/syspolicy` (`policy_keys.go`'s registry for types/scope/platforms, `util/syspolicy/policydoc` for labels/descriptions), the same generator and source of truth used for `docs/ios/policy/` and `docs/tvos/policy/`. Regenerate both files with:

```bash
go run tailscale.com/cmd/genpolicydocs
```

Do not hand-edit these files directly: edits will be overwritten the next time someone regenerates them. To change a key's label or description, edit `util/syspolicy/policydoc/policydoc.go`. To change a key's scope (Machine vs. Both) or Windows applicability, edit its `setting.NewDefinition(...)` call in `util/syspolicy/policy_keys.go`.

The hand-written files these replaced were compared against the generated output field-by-field before this change landed. To re-verify that comparison yourself, diff against the pre-generator version at `main`'s history prior to this change.

## What's different from the hand-written version

This mirrors the hand-written file's structure closely: `PreferenceOptionValue`/`VisibilityValue` keys still use native Enabled/Disabled radio buttons (Enabled/Disabled map mechanically onto each type's two "real" values, e.g. `always`/`never` or `show`/`hide`; leaving the policy Not Configured is what maps onto the third value, `user-decides`, since that's what Tailscale does when it sees no value at all), and the three settings that only make sense grouped together are still one GPO policy each: `AlwaysOn` (+ `AlwaysOn.OverrideWithReason`), `ExitNodeID` (+ `ExitNode.AllowOverride`), and `ManagedBy` (organization name, caption, support URL). That bundling isn't derivable from the flat `util/syspolicy` registry, so it's spelled out explicitly in `cmd/genpolicydocs/admx.go`'s `buildAlwaysOnPolicy`/`buildExitNodeIDPolicy`/`buildManagedByPolicy`.

Remaining differences, mechanical rather than curated:

- **Internal element IDs are derived directly from each key** (e.g. `ExitNodeID`, `ManagedByOrganizationName`) instead of the hand-written file's bespoke suffixed names (`ExitNodeIDPrompt`, `ManagedByOrganization`). These IDs are purely internal glue between the ADMX element and its ADML presentation entry, not shown to admins, so this has no visible or functional effect.
- **The old `DNSRegistration` bundle is gone.** Its outer Enabled/Disabled toggle never actually did anything (no `enabledValue`/`disabledValue` was ever defined for it), only its nested mode dropdown mattered. The generator drops the dead wrapper and treats the mode setting as a normal standalone `PreferenceOptionValue` key, `EnableDNSRegistration`. Unlike every other such key, its Disabled state maps onto `user-decides` rather than the generic `never`, since this key's unmanaged default is already `never` (see its doc comment in `util/syspolicy/pkey/pkey.go`): the two explicitly-settable states are the same `always`/`user-decides` pair the hand-written dropdown offered, just via a plain checkbox instead of a nested dropdown.
- **No version-introduced ("Tailscale version 1.56.0 and later") tracking, deliberately.** The hand-written file recorded which Tailscale version introduced each policy, but that data has no source anywhere in current Go code, generating it accurately would mean hand-curating a second table alongside the one already curated in `util/syspolicy/policydoc`, and letting it drift stale would be worse than not having it. Every generated policy uses one generic `supportedOn` reference instead. See https://tailscale.com/docs/features/tailscale-system-policies for which client version supports a given policy.
- **A different category split than the hand-written file's Top/UI/Settings.** Categories now come from `util/syspolicy/policydoc`'s `Category` field, one of five (`Configure the auto-update settings`, `Configure the exit node settings`, `Show contact information for your organization`, `Other settings`, `Change the visibility of UI items`), the verbatim section headings at https://tailscale.com/docs/features/tailscale-system-policies, so this file, `docs/ios/policy/`, and `docs/tvos/policy/` all group policies the same way instead of each format inventing its own. All five sit under one product-root "Tailscale" category, mirroring the hand-written file's two-level shape.
- **More keys than the hand-written file had.** The hand-written ADMX was built up incrementally and didn't cover every key in `util/syspolicy`; the generator includes every registered, Windows-supported key, so some previously-undocumented keys (e.g. `HardwareAttestation`, `MachineCertificateSubject`, `ExitNodeIP`, `Hostname`, `SuggestedExitNode`) now appear here for the first time.

## Keeping this file accurate

Same as `docs/ios/policy/`: platform applicability and scope live in `util/syspolicy/policy_keys.go`, labels, descriptions, and categories live in `util/syspolicy/policydoc/policydoc.go`, and https://tailscale.com/kb/1315/mdm-keys and https://tailscale.com/docs/features/tailscale-system-policies are the sources of truth for the latter. Platform filtering here checks for `"windows"` specifically, and is accurate for `VisibilityValue`-typed keys and a handful of others with unambiguous evidence, but most functional/behavioral keys default to "supported everywhere" (see `docs/ios/policy/README.md`'s Scope section for why that's an accepted tradeoff for now rather than an oversight).
